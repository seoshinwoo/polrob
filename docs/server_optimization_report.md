# PolRob 서버 최적화 리포트

## 요약

PolRob은 한 방에 최대 6명의 플레이어가 참여하는 실시간 멀티플레이 경찰과 도둑 게임이다. 방 하나의 인원 수가 작기 때문에, 이 프로젝트의 주요 서버 부하는 대규모 MMORPG처럼 한 공간 안의 수백 명을 필터링하는 AOI 문제보다는 여러 방에서 반복적으로 발생하는 이동 패킷 수신, 파싱, 브로드캐스트 비용에서 발생한다.

이번 서버 최적화는 다음 네 가지 병목을 중심으로 진행했다.

- 움직이지 않는 플레이어의 불필요한 이동 패킷 송신 감소
- UDP 이동 패킷 경량화
- 서버의 이동 브로드캐스트를 방 tick 단위로 묶어서 송신
- 서버 큐에 쌓인 이동 입력 중 같은 플레이어의 최신 입력만 처리

각 최적화는 공통 기준 커밋인 `32620197`과 비교했다. 테스트는 headless bot 기반 부하 테스트 스크립트로 수행했다.

```bash
./run_load_metrics.sh
```

테스트는 `60`, `300`, `600`, `900`개 봇으로 진행했다. 각 결과는 모든 예상 방이 `Playing` 상태이고 봇 실패가 없는 구간에서, 트래픽이 높은 20초 구간을 선택해 집계했다.

아래 표에서 `감소율`이 양수면 해당 부하가 줄었다는 뜻이고, 음수면 오히려 증가했다는 뜻이다.

## Baseline

기준 커밋은 `32620197`이다. 이 커밋에는 UDP 수신/송신 byte 측정 메트릭이 포함되어 있지만, 아래에서 비교하는 최적화 기능들은 적용되어 있지 않다.

주요 측정 지표는 다음과 같다.

- `CPU s/s`: 초당 CPU 사용량
- `Total packets/s`: `udp_recv/s + udp_send/s + tcp_send/s`
- `Total UDP bytes/s`: `udp_recv_bytes/s + udp_send_bytes/s`
- `GC alloc MB/s`: 초당 managed memory 할당량

## 1. Idle Player Send-Rate Reduction

### 변경 내용

플레이어가 움직이지 않을 때 클라이언트가 이동 업데이트를 더 낮은 빈도로 보내도록 변경했다. 실제 게임에서는 플레이어가 계속 이동하기만 하는 것이 아니라 잠깐 멈춰 숨거나 대기하는 상황이 있기 때문에, 같은 위치를 계속 보내는 패킷을 줄일 수 있다.

### 최적화 의도

서버가 필요로 하는 것은 최신 위치와 이동 상태다. 플레이어가 멈춰 있는 동안 동일한 위치를 반복해서 보내면 네트워크 패킷과 서버 수신 처리만 증가한다. 따라서 정지 상태에서는 송신 주기를 늦춰 불필요한 입력 트래픽을 줄였다.

### 결과

전체 기준으로 PPS는 소폭 감소했고 CPU도 감소했지만, UDP bytes는 모든 구간에서 일관되게 줄지는 않았다.

| Bots | CPU 감소율 | PPS 감소율 | UDP bytes 감소율 | GC alloc 감소율 |
|---:|---:|---:|---:|---:|
| 60 | -10.34% | 8.39% | 8.08% | 6.00% |
| 300 | -12.41% | 6.25% | 4.22% | 4.88% |
| 600 | 54.07% | -3.91% | -8.77% | -8.43% |
| 900 | -5.02% | 6.65% | 2.64% | 3.93% |
| Overall | 22.82% | 2.76% | -1.01% | -0.24% |

### 해석

이 최적화는 실제 플레이 패턴을 반영했다는 점에서 의미가 있다. 특히 숨기, 대기, 탐색처럼 플레이어가 자주 멈추는 게임에서는 불필요한 이동 패킷을 줄일 수 있다.

다만 효과는 플레이어 행동에 크게 의존한다. 모든 플레이어가 계속 움직이는 최악의 상황에서는 개선 폭이 작을 수 있다. 따라서 이 최적화는 "항상 큰 네트워크 절감 효과를 내는 최적화"라기보다, "현실적인 플레이 패턴에서 불필요한 입력 송신을 줄이는 최적화"로 설명하는 것이 정확하다.

## 2. Lightweight UDP Payload

### 변경 내용

이동 패킷에서 전체 `Player` JSON을 보내는 대신, 이동 동기화에 필요한 작은 payload만 보내도록 변경했다. 이름, 역할, 방 ID처럼 자주 변하지 않는 정보는 매 이동 패킷마다 보낼 필요가 없다.

### 최적화 의도

이동 패킷은 매우 자주 송수신된다. 따라서 패킷 하나의 크기를 줄이면 전체 네트워크 대역폭, 직렬화 비용, managed memory 할당량을 줄일 수 있다.

### 결과

이 최적화는 bandwidth 측면에서 가장 명확한 개선을 보였다. 전체 UDP bytes는 약 53% 감소했고, GC allocation은 약 39% 감소했다. 다만 패킷을 보내는 횟수 자체는 크게 바뀌지 않았기 때문에 PPS는 감소하지 않았다.

| Bots | CPU 감소율 | PPS 감소율 | UDP bytes 감소율 | GC alloc 감소율 |
|---:|---:|---:|---:|---:|
| 60 | -13.79% | -0.46% | 52.86% | 40.00% |
| 300 | -3.45% | -0.21% | 53.77% | 41.11% |
| 600 | 1.32% | -0.92% | 53.40% | 40.52% |
| 900 | -7.46% | -2.17% | 53.08% | 36.68% |
| Overall | -3.12% | -1.24% | 53.33% | 39.10% |

### 해석

이 최적화는 패킷 개수를 줄이는 최적화가 아니라, 패킷당 크기와 할당량을 줄이는 최적화다. 게임 반응성을 크게 건드리지 않으면서 매 이동 업데이트의 비용을 줄일 수 있다는 점에서 의미가 크다.

포트폴리오에서는 "UDP 이동 패킷을 경량화해 전체 UDP bytes를 약 53%, GC allocation을 약 39% 줄였다"라고 설명하는 것이 가장 적절하다.

## 3. Server Send Tick / State Sync Batching

### 변경 내용

서버가 클라이언트로부터 이동 패킷을 받을 때마다 즉시 다른 클라이언트에게 브로드캐스트하는 방식에서 벗어나, 방 단위 send tick에서 최신 이동 상태를 묶어 보내도록 변경했다.

### 최적화 의도

이동 입력이 들어올 때마다 즉시 브로드캐스트하면, 같은 플레이어의 연속된 위치 변화가 매우 짧은 간격으로 여러 번 전파될 수 있다. 하지만 다른 클라이언트 입장에서는 매 입력을 모두 즉시 받을 필요가 없고, 일정 주기마다 최신 위치를 받으면 보간을 통해 부드럽게 표현할 수 있다.

따라서 서버는 입력을 계속 받되, 송신은 방 tick에 맞춰 제어함으로써 중복 브로드캐스트를 줄였다.

### 결과

이 최적화는 CPU와 PPS 측면에서 가장 강한 개선을 보였다. 전체 CPU 사용량은 약 76%, 전체 PPS는 약 14%, 전체 UDP bytes는 약 12% 감소했다.

| Bots | CPU 감소율 | PPS 감소율 | UDP bytes 감소율 | GC alloc 감소율 |
|---:|---:|---:|---:|---:|
| 60 | 26.67% | 29.72% | 32.50% | 18.73% |
| 300 | 17.14% | 28.09% | 26.91% | 15.67% |
| 600 | 82.72% | 25.08% | 24.69% | 10.90% |
| 900 | 78.11% | -5.87% | -9.01% | -21.76% |
| Overall | 76.25% | 13.74% | 12.48% | -0.81% |

### 해석

이 최적화는 이번 작업 중 가장 중요한 서버 구조 개선이다. 서버 구조를 "입력마다 즉시 브로드캐스트"에서 "입력은 자주 받고, 송신은 제어된 tick에서 최신 상태를 배포"하는 형태로 바꾸었기 때문이다. 이는 실시간 게임 서버에서 흔히 사용하는 방식에 더 가깝다.

다만 900봇 구간에서는 UDP receive traffic 증가의 영향으로 total PPS와 UDP bytes가 오히려 증가했다. 그럼에도 CPU 개선은 크게 유지되었기 때문에, 이 최적화는 서버가 중복 상태를 처리하고 브로드캐스트하는 비용을 크게 줄였다고 해석할 수 있다.

## 4. Server Input Coalescing

### 변경 내용

방 command queue를 비울 때 같은 플레이어의 이동 명령이 여러 개 쌓여 있으면, 오래된 이동 명령을 모두 처리하지 않고 가장 최신 이동 명령만 적용하도록 변경했다.

### 최적화 의도

플레이어가 서버 tick 사이에 여러 이동 패킷을 보낸 경우, 서버가 오래된 모든 위치를 순서대로 처리할 필요는 없다. 이동 동기화에서 중요한 것은 대부분 최신 위치다. 따라서 같은 플레이어의 중복 이동 입력을 최신값 하나로 합쳐 서버 내부 처리량을 줄였다.

### 결과

이 최적화는 고부하에서 CPU를 크게 줄였다. 전체 CPU는 약 50% 감소했다. 하지만 클라이언트가 서버로 보내는 UDP 패킷 수 자체는 줄지 않기 때문에, PPS와 UDP bytes는 개선되지 않았고 일부 구간에서는 증가했다.

| Bots | CPU 감소율 | PPS 감소율 | UDP bytes 감소율 | GC alloc 감소율 |
|---:|---:|---:|---:|---:|
| 60 | 10.00% | 0.23% | 2.17% | -2.81% |
| 300 | -10.81% | 2.41% | 7.05% | -1.74% |
| 600 | 73.16% | -3.57% | -4.05% | -11.34% |
| 900 | 36.65% | -15.51% | -18.31% | -29.53% |
| Overall | 50.39% | -6.88% | -6.82% | -16.24% |

### 해석

이 최적화는 네트워크 PPS 최적화가 아니라 서버 내부 처리 비용 최적화다. 클라이언트는 여전히 같은 수의 UDP 패킷을 보내고, 서버도 그 패킷을 수신한다. 개선점은 서버가 큐에 쌓인 오래된 이동 입력을 모두 게임 상태에 적용하지 않아도 된다는 데 있다.

포트폴리오에서는 "UDP 입력 PPS를 줄였다"라고 쓰기보다, "같은 플레이어의 중복 이동 입력을 coalescing해 고부하 CPU 사용량을 약 50% 줄였다"라고 쓰는 것이 정확하다.

## 5. Final Combined Result

최종 결합 결과는 네 가지 최적화를 호환 가능한 형태로 하나의 브랜치에 병합한 뒤 다시 측정해야 한다.

예상되는 결합 효과는 다음과 같다.

- Idle send-rate reduction은 움직이지 않는 플레이어의 클라이언트 -> 서버 입력 패킷을 줄인다.
- Lightweight UDP payload는 패킷당 bytes와 GC allocation을 줄인다.
- Server send tick은 서버 -> 클라이언트 이동 브로드캐스트를 제어한다.
- Server input coalescing은 서버 내부에서 오래된 이동 입력을 처리하지 않도록 한다.

다만 위 결과들을 단순히 더해서 최종 성능 개선율로 보면 안 된다. 최적화끼리는 효과가 겹칠 수 있다. 예를 들어 server send tick이 이미 많은 중복 브로드캐스트를 줄였다면, input coalescing의 추가 PPS 개선 효과는 작을 수 있다. 반대로 CPU 처리 비용은 여전히 추가로 줄어들 수 있다.

최종 검증은 다음과 같은 방식으로 진행하는 것이 좋다.

```bash
./run_load_metrics.sh
```

- final optimized branch: 네 최적화를 병합한 브랜치
- bot counts: `60 300 600 900`

## 각 최적화의 한계

### Idle Player Send-Rate Reduction

플레이어 행동 패턴에 의존한다. 모든 플레이어가 계속 움직이는 상황에서는 개선 폭이 작다. 하지만 PolRob처럼 숨거나 멈추는 행동이 자연스러운 게임에서는 현실적인 최적화다.

### Lightweight UDP Payload

패킷 개수를 줄이는 것이 아니라 패킷 크기를 줄이는 최적화다. bandwidth와 GC allocation에는 효과가 크지만, PPS를 줄이려면 송신 주기 조절이나 batching이 함께 필요하다.

### Server Send Tick / State Sync Batching

송신 주기를 너무 낮추면 다른 플레이어 움직임이 덜 부드러워질 수 있다. 따라서 클라이언트 보간과 함께 적용해야 게임 플레이 품질을 유지할 수 있다.

### Server Input Coalescing

서버 내부 처리 비용은 줄이지만, 클라이언트가 보낸 UDP 패킷 수 자체는 줄이지 않는다. 또한 최신 이동 입력만 적용하는 방식이므로, 이동 경로 전체가 중요한 판정에는 조심해야 한다. 체포, 감옥, 승패 같은 핵심 게임 규칙은 서버 권위 기반으로 별도 검증되어야 한다.

### Benchmark Environment

이번 결과는 로컬 봇 테스트 기반이다. before/after 비교에는 충분히 의미가 있지만, 실제 서버 수용 인원 주장을 하려면 클라우드 VM 환경, 네트워크 지연, packet loss, 클라이언트 보간 품질까지 추가로 확인하는 것이 좋다.

## 포트폴리오 작성용 문단

PolRob의 실시간 이동 동기화 경로를 측정 기반으로 최적화했다. 먼저 headless bot 부하 테스트 환경을 구성해 60, 300, 600, 900개의 봇이 동시에 게임 플레이를 수행하도록 만들고, CPU 사용량, UDP/TCP PPS, UDP bytes/s, JSON 직렬화 횟수, GC allocation, 방 상태, 봇 실패 여부를 기록했다.

이후 동일한 baseline을 기준으로 네 가지 최적화를 독립적으로 적용하고 비교했다. 멈춘 플레이어의 이동 송신 주기 감소는 실제 플레이 패턴에서 발생하는 불필요한 입력 패킷을 줄이기 위한 최적화였고, UDP movement payload 경량화는 전체 UDP bytes를 약 53%, GC allocation을 약 39% 줄였다. 서버 이동 브로드캐스트를 방 tick 단위로 묶는 구조는 가장 큰 CPU/PPS 개선을 보였으며, 측정 결과 전체 CPU 사용량을 약 76%, total PPS를 약 14% 줄였다. 마지막으로 server input coalescing을 적용해 같은 플레이어의 오래된 이동 입력을 모두 처리하지 않고 최신 입력만 적용하도록 하여, 고부하 구간에서 전체 CPU 사용량을 약 50% 줄였다.

이번 최적화에서 중요한 점은 모든 최적화가 같은 종류의 부하를 줄이는 것은 아니라는 점이었다. 어떤 최적화는 패킷 크기를 줄이고, 어떤 최적화는 패킷 수를 줄이며, 어떤 최적화는 네트워크 트래픽은 그대로 두고 서버 CPU 처리 비용을 줄인다. 따라서 단순히 "서버 최적화"라고 표현하지 않고, 각 최적화가 어떤 병목을 개선했는지 CPU, PPS, UDP bytes, GC allocation 지표로 나누어 분석했다.
